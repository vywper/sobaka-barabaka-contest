# 1. T1 и T2: контейнер участника Hackathon Go1

Контейнер отвечает на `ping` и проверяет низкоуровневые команды Go1 в режиме `T2`.

# 2. Как работает запуск

```text
docker run IMAGE ping
    - /entrypoint.sh ping
    - python3 -m participant.ping
    - чтение /opt/participant/solution.json
    - проверка полей
    - один JSON-объект в stdout
    - завершение с кодом 0
```

**Образ** — подготовленная файловая система с программами. **Контейнер** — запущенный экземпляр этого образа. `Dockerfile` описывает сборку образа, а `entrypoint.sh` определяет, что делать при запуске контейнера.

Judge запускает контейнер через свой Python-запускатель и передаёт аргумент обязательному файлу `/entrypoint.sh`. Поэтому файл лежит именно в корне файловой системы контейнера. Настроек только в `compose.yaml` для официального запуска недостаточно; собственный Compose-файл этому проекту не требуется.

## Dockerfile

Базовый образ — `ros:humble-ros-base-jammy`: ROS 2 Humble на Ubuntu 22.04 Jammy. При сборке дополнительно устанавливается пакет `ros-humble-rmw-cyclonedds-cpp`.

Переменная `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` выбирает требуемую реализацию транспорта ROS 2. Установка пакета обеспечивает её наличие, а переменная выбирает её при запуске ROS-узлов.

Установка пакетов выполняется с правами root на этапе сборки. Затем `USER participant` переключает исполнение на пользователя с UID `10001`: при обычном запуске контейнер работает без root. Его домашняя папка — `/home/participant`, рабочая папка проекта — `/opt/participant`.

Все зависимости устанавливаются при сборке, когда доступ в интернет разрешён. В работающем контейнере нет установки пакетов или загрузки файлов из сети. GPU не используется.

## entrypoint.sh

Скрипт принимает ровно один аргумент. Ветка `ping` запускает Python-обработчик с помощью `exec`: Python заменяет процесс shell, а его код завершения становится кодом завершения контейнера.

Для `ping` не поднимаются ROS-узлы и не загружаются модели. Это помогает уложиться в лимит 10 секунд и получить чистый stdout.

В режиме `T2` скрипт подключает окружение ROS и запускает постоянный узел безопасности. Для T3–T5 скрипт сообщает об отсутствии реализации в stderr.

# 3. Подготовка Docker в Windows

Следующие команды предназначены для **PowerShell на хосте**, не для терминала внутри контейнера. Откройте PowerShell в папке проекта, где находится Dockerfile. 

# 4. Сборка образа

Из корня проекта выполните:

```powershell
docker build --platform linux/amd64 -t go1-shotigolova:t2-local .
```

Здесь `--platform linux/amd64` задаёт требуемую платформу, `-t` назначает локальное имя образу, а точка обозначает текущую папку как контекст сборки. На первой сборке нужен интернет: Docker скачивает базовый образ и ROS-пакеты. Повторные сборки используют кэш.

С явным контекстом:

```powershell
docker --context desktop-linux build --platform linux/amd64 -t go1-shotigolova:t2-local .
```

# 5. Проверка контейнера

Вызов точки входа:

```powershell
docker --context desktop-linux run --rm --network none --entrypoint /entrypoint.sh go1-shotigolova:t2-local ping
```

`--rm` удаляет контейнер после завершения. 
`--network none` отключает внешнюю сеть; 
дополнительных томов, файлов с компьютера или GPU для этого запуска не требуется.

Чтобы результат `ping` для образа Т2 остался в списке Docker Desktop, дай контейнеру свободное имя:

```powershell
docker --context desktop-linux run --name vibrant_golova_t2 --network none go1-shotigolova:t2-local ping
```

После печати JSON контейнер ожидаемо получит статус `Exited (0)`, поскольку `ping` — одноразовая проверка. Повторить запуск того же контейнера и увидеть вывод можно так:

```powershell
docker --context desktop-linux start -a vibrant_golova_t2
```

Запуск выше проверяет протокол `ping`. Для испытания движения и удержания запусти проверку Т2 ниже.

## 6. Как работает Т2

`/lowcmd_bare` → проверка чисел и диапазонов → ограничение шага → проверка самоколлизий → `/lowcmd`.

- `t2_safety.py` проверяет `q`, `dq`, `kp`, `kd` и `tau` и вычисляет следующий шаг для 12 суставов. Шаг считается от последней опубликованной цели и сохраняет направление исходного движения.
- `t2_collision.py` загружает модель Go1 из ТЗ, выбирает 655 пар из таблицы организаторов и проверяет позы с шагом до 0,1°. Опасный контакт — проникновение глубже 1 мм.
- `t2_node.py` принимает ROS-сообщения и публикует команды по `/clock`. Пока отдельный поток считает контакты, узел продолжает выдавать ранее принятую команду или режим удержания. При коллизии или отсутствии свежей пригодной команды в течение 450 мс цель сохраняется, `dq` и `tau` становятся нулевыми, а `kp` и `kd` принимают значения 40 и 2.

При сборке Dockerfile фиксирует версию ROS-сообщений Unitree, модель, пары контактов и MuJoCo 3.3.7. Обе модели используют одну геометрию. Simulator применяет команды к роботу, а Participant проверяет цели через расчёт контактов.

## 7. Локальные тесты

Из папки проекта в PowerShell выполни следующие команды.

```powershell
python -B -m unittest discover -s tests -p test_t2_safety.py -v
python -B tests/run_t2_sim.py --context desktop-linux --image go1-shotigolova:t2-local
```

Первый тест проверяет правила фильтра на обычном Python. Второй при необходимости скачивает образ публичного симулятора с закреплённым digest, запускает сцену MuJoCo `lowlevel` и проверяет блок через ROS. Программа выводит время включения удержания, частоту `/lowcmd`, максимальный интервал и количество проверенных сообщений. Контейнеры проверки удаляются после завершения. Загрузка образа нужна только перед первым запуском.

Критерии теста — не менее 50 Гц за 5 с, интервал не больше 100 мс, удержание за 0,5 с. Время измеряется по `/clock`. Проверка использует публичную сцену и собственные входные примеры. [ТЗ T2](https://github.com/Urika000/go1-simulator-public/blob/main/docs/parts_of_tz/%D0%A2%D0%97_T2.pdf)
